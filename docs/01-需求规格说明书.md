## 0. 需求解读与关键假设

原始需求只有一句话：**"当提交非 merge 内容时，检查是否是指定分支，不是则打断提交并提示"**。其中有两处必须显式定义，否则无法验收。

### 0.1 「指定分支」的两种业务解释

| 解释 | 规则语义 | 典型场景 | 本文处理 |
|---|---|---|---|
| **A. 白名单**（字面理解） | 只有列出的分支允许直接提交，其余全部拦截 | 团队只允许在 `dev` / `feature/*` 上开发 | ✅ 作为默认模式 |
| **B. 黑名单 / 保护分支** | 列出的分支禁止直接提交，其余放行 | 保护 `main` / `master` / `release/*`，必须走 MR | ✅ 同时实现，切换下拉即可 |

**两者共用同一套匹配引擎，仅判定方向相反**，实现成本几乎为零。默认按字面取 A，**建议评审时明确**（见 §13 Q1）。

### 0.2 「非 merge 内容」的两种解释

| 解释 | 判定方式 | 本文处理 |
|---|---|---|
| **A. 本次提交是合并提交** | `GitRepository#getState() == MERGING` | ✅ v1.0 采用 |
| B. 提交的变更中不含合并产生的改动 | 需比对 `MERGE_HEAD` 与 index 差异，实现复杂且有误判 | ⏭ v1.1 评估 |

即：**"处于合并状态时的提交"整单放行**。已知副作用：合并期间顺带勾选的其他文件也会被放行（见 §12 已知限制）。

### 0.3 其他假设

- 使用场景是 **Git**（不覆盖 SVN / Mercurial）。
- 只在 **IDE 内提交**生效；命令行提交不在范围内（由服务端保护分支兜底）。
- 插件定位是 **"防误操作护栏"**，不是安全管控手段。

## 1. 背景与问题

### 1.1 现状

团队采用主干保护 + MR 评审流程，但保护规则只配置在服务端。开发者本地仍可：

1. 在 `main` 上直接修改并 `commit`，直到 `push` 才被拒绝；
2. 此时本地已产生提交，需要 `reset` / 新建分支 / cherry-pick 才能恢复，**平均处理成本 10–30 分钟**；
3. 多人共用一台机器或临时排查线上问题时，误提交概率更高。

### 1.2 问题定义

> 保护规则**反馈太晚**。错误在"提交"这一刻已经发生，但提示在"推送"时才出现，中间存在一段"已污染本地历史"的窗口。

### 1.3 解决思路

把反馈提前到 **commit 动作发生的瞬间**，用 IDE 原生对话框阻断，并提供一键跳转配置的入口。

## 2. 目标与非目标

### 2.1 目标（Goals）

| ID | 目标 | 度量 |
|---|---|---|
| G1 | 在受保护/非允许分支上阻止直接提交 | 拦截成功率 100%（规则命中时） |
| G2 | 不误伤合法的合并提交 | merge 状态下 0 误拦 |
| G3 | 提示信息足以让用户自助解决 | 用户无需查文档即可知道下一步；≥ 80% 场景一次操作解决 |
| G4 | 规则可团队共享、可评审 | 配置随仓库提交，改动出现在 MR diff 中 |

### 2.2 非目标（Non-Goals）

| 不做 | 原因 |
|---|---|
| 替代服务端保护分支 | 本地插件可被禁用，不构成安全边界 |
| 校验提交信息格式 / 关联工单号 | 已有 commit message 检查或服务端规则，避免功能重叠 |
| 阻止 `push` | push 阶段由服务端负责，插件重复实现收益低 |
| 代码质量检查（lint / 静态分析） | 与职责无关 |
| 覆盖命令行 / 其他 Git 客户端 | 由 pre-commit hook 或服务端兜底 |

## 3. 术语表

| 术语 | 含义 |
|---|---|
| 受保护分支 | 黑名单模式下，禁止直接提交的分支（如 `main`） |
| 允许分支 | 白名单模式下，允许直接提交的分支（如 `dev`、`feature/*`） |
| 合并提交（merge commit） | 处于 Git `MERGING` 状态时产生的提交，含两个及以上父提交 |
| 分离 HEAD（detached HEAD） | 当前不在任何分支上，`getCurrentBranch()` 返回 `null` |
| 规则模式 | 白名单（WHITELIST）/ 黑名单（BLACKLIST） |
| 提交面板 | Commit 工具窗口 / Commit Changes 对话框中勾选的待提交文件集合 |

## 4. 角色与场景

| 角色 | 诉求 | 典型场景 |
|---|---|---|
| 业务开发 | 不想被误拦，也不想误提交 | 在 `feature/order-123` 上正常提交；切到 `main` 改配置时被拦下 |
| 技术负责人 | 规则可维护、可评审 | 在 MR 中新增一条保护规则 `release/*` |
| SCM / 运维 | 不被本地绕过 | 服务端保护分支仍然生效 |

### 用户故事

- **US-1**：作为开发，我在 `main` 上误点提交时，希望**立刻**被拦下并被告知当前分支不能提交，而不是等到 push 才发现。
- **US-2**：作为开发，我在合并 `release` 分支解决冲突后提交，希望**不被**规则误拦。
- **US-3**：作为技术负责人，我希望规则写在仓库里，改规则走 MR，而不是每个人本地各配一套。

## 5. 业务流程

```mermaid
flowchart TD
    A[用户点击 Commit / Commit and Push] --> B{插件已启用?}
    B -- 否 --> Z[放行提交]
    B -- 是 --> C[取本次提交涉及的文件]
    C --> D[按 Git 仓库分组]
    D --> E{仓库处于 MERGING?}
    E -- 是且允许合并豁免 --> Z
    E -- 否 --> F[读取当前分支名]
    F --> G{分离 HEAD?}
    G -- 是 --> H{拦截分离 HEAD?}
    H -- 是 --> X[记录违规]
    H -- 否 --> Z
    G -- 否 --> I[按模式匹配规则]
    I -- 白名单: 未命中<br/>黑名单: 命中 --> X
    I -- 通过 --> Z
    X --> J[汇总全部违规仓库]
    J --> K[弹窗: 列出分支/仓库/原因]
    K --> L[返回 CANCEL, 提交中止]
    L --> M{用户点击"查看规则设置"?}
    M -- 是 --> N[打开 Settings → Branch Guard]
    M -- 否 --> O[结束]
```

## 6. 功能需求

> 优先级：**P0** = MVP 必须；**P1** = 首个迭代内建议；**P2** = 可延后。

### FR-01 提交前拦截 · P0

| 项 | 内容 |
|---|---|
| 描述 | 在用户执行提交（含 Commit、Commit and Push、Amend）时，于真正写入仓库**之前**执行校验；校验不通过则中止本次提交，仓库状态不发生任何变化 |
| 触发点 | 平台提交前置检查扩展点（`CheckinHandler#beforeCheckin`） |
| 覆盖入口 | ① 非模态 Commit 工具窗口；② 模态 Commit Changes 对话框；③ "Commit and Push"；④ Amend Commit |
| 不覆盖 | 命令行 `git commit`、Shelve / Patch 操作、Revert 操作 |
| 验收 | 规则命中时，`git log` 无新提交，工作区变更保持原样，提交面板内容不丢失 |

### FR-02 分支规则匹配 · P0

| 项 | 内容 |
|---|---|
| 描述 | 支持两种互斥模式：白名单（仅列出的分支可提交）、黑名单（列出的分支禁止提交） |
| 匹配对象 | 当前分支的**短名**（如 `feature/order-123`），不含 `refs/heads/` 前缀与远程名前缀 |
| 通配符 | `*` 匹配任意字符（**含 `/`**）；`?` 匹配单个字符；其余字符按字面量处理，大小写敏感 |
| 示例 | `feature/*` 命中 `feature/a`、`feature/a/b`；`release/*` 命中 `release/2.3`；`main` 仅命中 `main` |
| 空规则 | 规则列表为空时**不拦截**（视为未配置），避免"装了就锁死" |
| 验收 | 见 §11 AC-02 ~ AC-04 |

### FR-03 合并提交豁免 · P0

| 项 | 内容 |
|---|---|
| 描述 | 当仓库处于 `MERGING` 状态时，跳过分支规则校验，直接放行 |
| 可配置 | 开关 `allowMergeCommits`，默认 **开** |
| 关闭后 | 合并提交同样受规则约束（用于"连合并也必须走 MR"的严格团队） |
| 验收 | AC-05 |

### FR-04 多仓库分别判定 · P0

| 项 | 内容 |
|---|---|
| 描述 | 一个项目可能包含多个 Git 仓库（multi-root / 子模块）。按仓库分别判定，**任一仓库违规即阻断整次提交** |
| 提示 | 弹窗中列出**全部**违规仓库及其分支，不只报第一个 |
| 非 Git 文件 | 无法映射到 Git 仓库的文件（如混合 SVN 项目）直接忽略，不参与判定、不报错 |
| 验收 | AC-06 |

### FR-05 部分提交支持 · P0

| 项 | 内容 |
|---|---|
| 描述 | 只校验**本次勾选**的文件所属仓库，而非项目全部仓库 |
| 理由 | 避免"未参与本次提交、分支不合规的仓库"造成误拦 |
| 验收 | 仓库 A（合规）+ 仓库 B（不合规）中只勾选 A 的文件 → 放行 |

### FR-06 分离 HEAD 处理 · P1

| 项 | 内容 |
|---|---|
| 描述 | 当前不在任何分支上（`getCurrentBranch() == null`）时，默认**拦截**并提示"当前处于分离 HEAD 状态，请先切到分支" |
| 可配置 | 开关 `blockDetachedHead`，默认 **开** |
| 理由 | 分离 HEAD 下的提交极易丢失（无分支引用），属于高风险操作 |
| 验收 | AC-07 |

### FR-07 阻断提示与引导 · P0

| 项 | 内容 |
|---|---|
| 描述 | 阻断时弹出错误图标对话框，内容必须包含 4 要素 |
| 要素 | ① 结论（本次提交已被阻止）；② 违规仓库路径；③ 当前分支名与违规原因（受保护 / 不在允许列表 / 分离 HEAD）；④ 下一步建议（切分支 / 走合并 / 修改规则） |
| 按钮 | `[查看规则设置]`（打开设置页后仍保持中止）、`[取消提交]`（默认按钮） |
| 文案 | 见 §14；需支持中英文 |
| 验收 | AC-08 |

### FR-08 规则配置界面 · P0

| 项 | 内容 |
|---|---|
| 位置 | `Settings/Preferences → Branch Guard`（项目级） |
| 控件 | 启用开关、模式下拉、分支规则多行文本框（每行一条）、合并豁免开关、分离 HEAD 拦截开关、自定义提示语（可选） |
| 交互 | 实时校验不合法输入（空行忽略、`#` 开头视为注释）；`Apply` 后立即生效，无需重启 |
| 验收 | AC-09 |

### FR-09 配置持久化与团队共享 · P0

| 项 | 内容 |
|---|---|
| 存储 | 项目级，写入 `<项目>/.idea/branch-guard.xml` |
| 共享 | 该文件应随仓库提交（` .idea` 已被版本控制时无需额外操作）；文档需说明 |
| 缺失时 | 文件不存在时使用内置默认值，不报错 |
| 冲突 | 多人同时修改以最后一次 `Apply` 为准（IDE 自身设置文件的通用行为） |
| 验收 | AC-10 |

### FR-10 全局开关 · P1

| 项 | 内容 |
|---|---|
| 描述 | `enabled=false` 时插件完全不介入，等同于未安装 |
| 用途 | 紧急 hotfix、演示、排障 |
| 审计 | 关闭状态在设置页顶部以警示条显示（"规则已停用，提交不会被校验"） |

### FR-11 非 Git 场景静默 · P0

| 项 | 内容 |
|---|---|
| 描述 | 项目中没有任何 Git 仓库时，不注册处理器、不弹窗、不产生日志噪音 |
| 验收 | 纯 Maven（SVN）项目提交无任何感知 |

### FR-12 异常容错（Fail-Open） · P0

| 项 | 内容 |
|---|---|
| 描述 | 插件内部发生任何未预期异常时，**记录日志并放行提交**，绝不因插件故障阻塞用户 |
| 理由 | 本地护栏的价值是"减少麻烦"，不能反过来制造麻烦 |
| 日志 | `Logger.getInstance(...).warn(...)`，包含异常栈，便于反馈 |
| 验收 | 人为制造异常（如规则含非法正则）→ 提交成功 + 日志有 WARN |

### FR-13 本地临时放行 · P2（v1.1）

| 项 | 内容 |
|---|---|
| 描述 | 允许对**单次提交**放行，需填写原因，并在提交信息末尾追加 `Branch-Guard-Bypass: <原因>` |
| 状态 | **v1.0 不做**。理由：需求明确要求"打断"，先建立规则权威性；放行能力需配合审计，否则形同虚设 |
| 备注 | 若评审认为必须，可作为 P1 插入，工作量 +0.5 人日 |

## 7. 规则决策表

设：`E`=启用，`M`=规则模式，`G`=处于 MERGING，`D`=分离 HEAD，`X`=分支命中规则列表。

| # | E | G（且豁免开启） | D | M | X | 结果 | 原因码 |
|---|---|---|---|---|---|---|---|
| 1 | 否 | - | - | - | - | 放行 | DISABLED |
| 2 | 是 | 是 | - | - | - | 放行 | MERGE_COMMIT |
| 3 | 是 | 否 | 是 | - | - | 拦截（若 `blockDetachedHead`）/ 放行 | DETACHED_HEAD |
| 4 | 是 | 否 | 否 | 白名单 | 是 | 放行 | BRANCH_ALLOWED |
| 5 | 是 | 否 | 否 | 白名单 | 否 | **拦截** | BRANCH_NOT_ALLOWED |
| 6 | 是 | 否 | 否 | 黑名单 | 是 | **拦截** | PROTECTED_BRANCH |
| 7 | 是 | 否 | 否 | 黑名单 | 否 | 放行 | OK |
| 8 | 是 | 否 | 否 | 任意 | 规则为空 | 放行 | NO_BRANCH_RULES |

> 判定顺序：`E` → `G` → `D` → `M/X`。顺序不可调换，否则"合并提交被分支规则拦下"。

## 8. 配置项定义

| 键 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `enabled` | boolean | `true` | 总开关 |
| `mode` | enum | `WHITELIST` | `WHITELIST` / `BLACKLIST` |
| `patterns` | list\<string\> | `dev`, `develop`, `feature/*`, `hotfix/*` | 分支规则，每行一条，`#` 开头为注释 |
| `allowMergeCommits` | boolean | `true` | 合并提交豁免 |
| `blockDetachedHead` | boolean | `true` | 分离 HEAD 是否拦截 |
| `blockMessage` | string | 空 | 自定义提示语，为空时使用内置文案 |
| `messageLanguage` | enum | `FOLLOW_IDE` | 阻断弹窗语言：`FOLLOW_IDE` / `ZH_CN` / `EN`。**仅影响弹窗**，设置页始终跟随 IDE |

`branch-guard.xml` 示例：

```xml
<project version="4">
  <component name="BranchGuardSettings">
    <option name="enabled" value="true" />
    <option name="mode" value="BLACKLIST" />
    <option name="allowMergeCommits" value="true" />
    <option name="blockDetachedHead" value="true" />
    <option name="messageLanguage" value="FOLLOW_IDE" />
    <option name="patterns">
      <list>
        <option value="main" />
        <option value="master" />
        <option value="release/*" />
      </list>
    </option>
  </component>
</project>
```

| NFR-09 | 体积 | 插件包 < 200 KB | `buildPlugin` 产物 |

## 10. 异常与边界场景

| # | 场景 | 期望行为 |
|---|---|---|
| E-01 | 分支名含中文/空格/特殊字符 | 按字面量匹配，不报错 |
| E-02 | 规则行含非法字符（如 `[`） | 视为字面量转义处理，不抛异常 |
| E-03 | 规则全为空行 / 全是注释 | 等同于未配置 → 放行 |
| E-04 | 仓库尚无任何提交（unborn HEAD） | `getCurrentBranch()` 可能返回分支名但无 commit；按分支名正常判定，不报错 |
| E-05 | 提交时仓库正在 rebase | `State=REBASING`，非 MERGING → 按分支规则判定（默认会拦截受保护分支） |
| E-06 | 提交时仓库正在 cherry-pick | 同 E-05 |
| E-07 | 合并冲突未解决就提交 | IDE 本身会阻止；本插件不重复处理 |
| E-08 | 空提交（无文件） | 跳过校验，放行 |
| E-09 | 在设置页把模式改空/删光规则 | 视为未配置，放行，并在设置页提示 |
| E-10 | 用户在两台机器上规则不同 | 以各自 `.idea/branch-guard.xml` 为准；文档提示"规则变更需提交" |
| E-11 | 项目根目录不是仓库根（子目录打开） | `getVcsRootFor` 返回真实仓库根，正常判定 |
| E-12 | Git 插件被禁用 | 平台不加载本插件（依赖不满足），不报错 |

## 11. 验收标准（Given / When / Then）

| ID | Given | When | Then |
|---|---|---|---|
| AC-01 | 黑名单模式，规则 `main`，当前分支 `main`，有未提交改动 | 点击 Commit | 提交被中止；仓库无新提交；工作区改动保留；弹出阻断提示 |
| AC-02 | 白名单模式，规则 `dev`、`feature/*`，当前分支 `feature/login` | 点击 Commit | 提交成功 |

## 14. 附录：提示文案

### 阻断弹窗（中文）

```
Branch Guard 已阻止本次提交

以下仓库的当前分支不允许直接提交：
  • order-service — 分支 release/2.3（受保护分支，禁止直接提交）
  • common-lib — 分支 main（受保护分支，禁止直接提交）

合并（merge）提交不受此限制。
建议：切换到 feature/* 分支后重新提交，或通过合并方式更新该分支。

[ 查看规则设置 ]  [ 取消提交 ]
```

### 文案变体

| 原因码 | 标题行 | 建议行 |
|---|---|---|
| `PROTECTED_BRANCH` | 分支 {0} 是受保护分支，禁止直接提交 | 请切换到特性分支，或通过合并方式更新 |
| `BRANCH_NOT_ALLOWED` | 分支 {0} 不在允许直接提交的列表中 | 请切换到 {1} 等允许的分支 |
| `DETACHED_HEAD` | 当前处于分离 HEAD 状态 | 请先切换/新建分支，避免提交丢失 |

### 设置页文案

- 启用开关：`启用提交前分支校验`
- 模式：`规则模式` → `白名单：仅列出的分支可提交` / `黑名单：列出的分支禁止提交`
- 规则框：`分支规则（每行一条，支持 * 和 ? 通配符，# 开头为注释）`
- 停用警示条：`规则已停用，提交不会被校验。`
