# 00 · 可行性分析与方案选型

> 项目：IDEA 插件 **Branch Guard（分支守卫）**
> 目标：提交前校验当前 Git 分支，非 merge 提交在不符合规则时阻断并提示
> 技术栈：Java + IntelliJ Platform SDK
> 版本：v1.0 / 2026-10-20
> 结论：**技术可行**，MVP 约 **7 人日**（含 20% buffer 约 8.5 人日）

---

## 1. 一句话结论

平台提供了**官方、稳定、带扩展点**的提交拦截机制（`CheckinHandler.beforeCheckin()` 返回 `ReturnResult.CANCEL`），Git 插件提供了**纯 API 的分支与仓库状态读取能力**（`GitRepository#getCurrentBranch()` / `#getState()`）。二者组合即可完整实现需求，**无需调用 git 命令行、无需修改 IDE 源码、无需依赖 hack 手段**。

真正的风险不在"能不能拦"，而在三处工程细节：

| 风险点 | 说明 | 影响 |
|---|---|---|
| 拦截时机 | 2025.1 起 IDEA 默认使用**非模态（non-modal）提交**，`beforeCheckin` 中弹模态框需验证 | 中高 |
| 定位预期 | 插件属于**本地误操作防护**，不是安全管控（用户可禁用插件） | 中 |
| merge 判定边界 | amend 后的合并提交、squash merge 等场景不产生 `MERGING` 状态 | 中 |

## 2. 需求拆解与技术映射

把需求拆成 4 个原子能力，逐一确认平台支撑：

| # | 能力 | 平台机制 | 成熟度 | 结论 |
|---|---|---|---|---|
| C1 | 捕获"用户点击提交"这一时机，并能否决 | 扩展点 `com.intellij.checkinHandlerFactory` → `CheckinHandler#beforeCheckin()` → `ReturnResult.CANCEL` | 稳定 API，自 2005 年起存在 | ✅ |
| C2 | 读取当前分支名、判断是否处于 merge 中 | `GitRepositoryManager#getRepositories()` → `GitRepository#getCurrentBranch()` / `#getState() == MERGING` | 稳定 API，Git 插件公开接口 | ✅ |
| C3 | 让"哪些分支允许/禁止"可配置 | 项目级 `PersistentStateComponent` + `Configurable` 设置页 | 平台标准做法 | ✅ |
| C4 | 中断并给出可读提示，最好能直达设置 | `Messages.showDialog(...)` + `ShowSettingsUtil` | 稳定 API | ✅ |

**四项能力全部有官方 API 支撑，无一项需要反射或内部 API（`@Internal`）。**

### 2.1 C1 的直接证据（源码级）

`platform/vcs-api/src/com/intellij/openapi/vcs/checkin/CheckinHandlerFactory.java`（intellij-community，2026-10 核对）：

```java
public abstract class CheckinHandlerFactory implements BaseCheckinHandlerFactory {
  public static final ExtensionPointName<CheckinHandlerFactory> EP_NAME =
      ExtensionPointName.create("com.intellij.checkinHandlerFactory");

  public abstract @NotNull CheckinHandler createHandler(@NotNull CheckinProjectPanel panel,
                                                        @NotNull CommitContext commitContext);
}
```

`CheckinHandler.java` 中：

```java
public enum ReturnResult { COMMIT, CANCEL, CLOSE_WINDOW }

/**
 * This method will not be called if {@link CommitCheck} interface is implemented.
 */
public @Nullable ReturnResult beforeCheckin(@Nullable CommitExecutor executor, ...) {
    return beforeCheckin();
}
public ReturnResult beforeCheckin() { return ReturnResult.COMMIT; }
```

`CANCEL` 的语义就是**中止本次提交**（含 "Commit and Push" 链路），这是平台为"提交前置检查"设计的正式返回码，不是副作用。

> 同一扩展点的官方使用范例：`CodeAnalysisBeforeCheckinHandler`（提交前代码分析）、`TodoCheckinHandler`（提交前 TODO 检查）、`UpdateCopyrightCheckinHandlerFactory`。说明"检查不通过就阻断"是平台认可的标准用例。

### 2.2 C2 的直接证据

`git4idea.repo.GitRepository`（Git 插件公开接口，非 internal）：

```java
VirtualFile getRoot();
@Nullable GitBranch getCurrentBranch();   // 分离 HEAD 时为 null
String getCurrentBranchName();
GitRepository.State getState();           // CLEAN / MERGING / REBASING / CHERRY_PICKING / ...
```

`git4idea.repo.GitRepositoryManager`：

```java
static GitRepositoryManager getInstance(Project project);
Collection<GitRepository> getRepositories();
@Nullable GitRepository getRepositoryForRoot(@Nullable VirtualFile root);
```

**merge 判定**采用 `repo.getState() == GitRepository.State.MERGING`。这是 IDE 自身在合并期间于状态栏显示 "Merging…" 的同一数据源，比自己解析 `.git/MERGE_HEAD` 更可靠。

### 2.3 关于"新的异步提交检查 API"

平台自 2023.1 起引入 `com.intellij.openapi.vcs.checkin.CommitCheck`：

```kotlin
interface CommitCheck : PossiblyDumbAware {
  fun getExecutionOrder(): ExecutionOrder
  fun isEnabled(): Boolean
  suspend fun runCheck(commitInfo: CommitInfo): CommitProblem?
}
```

它是 `beforeCheckin` 的**继任者**，更适合非模态提交（可后台执行、非模态报错）。但它有两个约束：

1. 以 **Kotlin `suspend`** 函数暴露，Java 实现需要手写 `Continuation` 参数，可读性与稳定性都差；
2. 需要返回 `CommitProblem` 对象，提示交互被平台接管（自定义"跳转设置"按钮受限）。

由于本插件的检查是**纯内存读取**（微秒级，无 IO、无网络），不存在"需要异步"的性能诉求，因此 **MVP 采用 `CheckinHandler`，把 `CommitCheck` 列为演进项**。该决策已隔离在 `BranchGuardCheckinHandler` 单一类中，未来替换成本 < 1 人日。

## 3. 方案选型：为什么是 IDE 插件

同一个需求有 4 种落地方式，按"能否在用户点提交的瞬间拦住"排序对比：

| 维度 | A. IDEA 插件（本方案） | B. Git pre-commit hook | C. 服务端保护分支 / push rule | D. Inspection 检查 |
|---|---|---|---|---|
| 拦截时机 | 点"提交"瞬间 | `git commit` 瞬间 | `git push` 时 | 编码时提示 |
| 与 IDE 集成 | 原生（提交面板、设置页、可跳转） | 需脚本，输出在控制台 | 无（远端拒绝） | 原生 |
| IDE 内可被绕过 | 需禁用插件（有感知） | **IDE 可直接跳过 hooks** | 不可绕过 | 仅提示不阻断 |
| 团队配置共享 | `.idea/branch-guard.xml` 随仓库 | `core.hooksPath` + 仓库脚本 | 服务端统一 | 随项目 |
| 覆盖非 IDE 提交（命令行 / 其他客户端） | ❌ | ✅ | ✅ | ❌ |
| 维护成本 | 中（需随 IDE 版本验证） | 低 | 低 | 低 |
| 综合评分（5 分制加总） | **19 / 25** | 16 / 25 | 17 / 25 | 11 / 25 |

**关键事实**：IntelliJ IDEA **2025.1 新增了"禁用 Git commit hooks 运行"的选项**（Settings | Advanced Settings | Version Control | Git）。这意味着 hook 方案在 IDEA 内**可以被用户无感关闭**，可靠性低于"提交前插件校验"。

### 推荐组合（纵深防御）

```
开发者点提交
   │
   ├─[第 1 道] IDEA 插件 Branch Guard ── 立即阻断 + 引导切分支（本方案，体验最好）
   │
   ├─[第 2 道] Git pre-commit hook ───── 覆盖命令行提交（可选，复用同一份规则文件）
   │
   └─[第 3 道] 服务端保护分支 ────────── 最终兜底，任何客户端都绕不过（强烈建议同时开启）
```

**结论**：插件是"体验最优的第 1 道闸"，但不能也不应该替代服务端保护分支。文档中需明确这一产品定位，避免验收时被当作安全控件考核。

## 4. 兼容性与构建可行性

### 4.1 版本矩阵与实际取舍

| IDE 版本 | 平台分支 | 平台 JDK | 本插件 |
|---|---|---|---|
| 2023.3 – 2026.1 | 233 – 261 | 17 / 21 | ⚠️ 不支持（当前产物 class 69，高于 61/65） |
| **2026.2+** | **262** | **25** | ✅ 构建目标（本机 2026.2.1 实测通过） |

**为什么最终没有用"最低版本编译"**：原计划用 2023.3.8 SDK + `--release 17` 覆盖最大范围，但本机只有 2026.2.1，其平台类是 **class 69（Java 25）**，`--release 17` 的编译器直接拒绝：

```text
error: class file has wrong version 69.0, should be 61.0
```

要覆盖 2023.3，需另外下载 2023.3.8 的 SDK（约 1 GB）。**当前策略**：`--release 25` + `since-build=262`，只支持 2026.2+；切换旧版只需三处同改（`idea.home` / `platform.release` / `since.build`），见开发文档 §2、§14。

### 4.2 构建工具链（Maven，2026-10 实测）

| 组件 | 版本 | 说明 |
|---|---|---|
| Maven | **3.9.16** | 本机实测可用 |
| 运行 Maven 的 JDK | **25**（IDEA 自带 JBR 25.0.3） | ⚠️ 本机默认 JDK 8，不切 `JAVA_HOME` 会失败；JBR 自带 `javac` |
| 编译目标 | `--release 25` | 与平台 class 版本一致 |
| 单元测试 | JUnit 5 + Surefire 3.2.x | 19 个纯逻辑用例，全部通过 |
| 打包 | `maven-assembly-plugin` | 产出 31 KB、`branch-guard/lib/<jar>` 结构的 zip |
| `until-build` | **不设置** | 兼容未来版本，靠 Plugin Verifier 提前发现不兼容 |

#### 4.2.1 为什么 Maven 需要自建构建链

| 事实 | 证据 | 影响 |
|---|---|---|
| JetBrains 官方只维护 Gradle 构建链 | 官方支持论坛明确回复："The official way of developing plugins is using Gradle… We do not have plans for supporting Maven in plugin development" | 没有 `runIde` / `buildPlugin` / `verifyPlugin` / `signPlugin` 现成目标 |
| Maven Central 无官方 Maven 插件 | 检索 `intellij-platform-maven-plugin`、`intellij-maven-plugin` 均返回 **0 条**；GitHub 亦无对应仓库 | 无法靠引入一个 `<plugin>` 解决 |
| 平台以「IDE 整包 zip」发布 | JetBrains *Artifacts Repositories* 文档：`com.jetbrains.intellij.idea:ideaIC:<ver>:zip`；`git4idea` 是捆绑插件，不单独发布 | 编译 classpath 实际要落到本地发行包 |

因此 Maven 方案用三件事补齐，**构建与打包全部收敛在 `pom.xml`**：

1. **编译**：Ant `javac` + `fileset` 通配（`lib/*.jar`、`plugins/vcs-git/lib/*.jar`、`plugins/git4idea/lib/*.jar`），不写死 jar 名，同时覆盖 2023.3–2025.x 与 2026.x 两种目录布局；
2. **打包**：`maven-assembly-plugin` 产出 `branch-guard/lib/<plugin>.jar` 结构的插件 zip（**必须有顶层目录**）；
3. **运行 / 验证**：本地用 IDEA 原生 Plugin Run Configuration 调试，兼容性用 Plugin Verifier CLI 手工跑。

> 代价：比 Gradle 方案多约 **0.5 人日**一次性投入，且失去四个开箱任务。对内部插件可接受。

### 4.3 依赖声明

```xml
<depends>com.intellij.modules.platform</depends>
<depends>Git4Idea</depends>
```

`Git4Idea` 是 Git 插件的 **plugin id**。注意 2026.2 中插件**目录**已改为 `plugins/vcs-git/`，但 jar 内 `plugin.xml` 的 `<id>` 仍是 `Git4Idea`（已实测）。编译期必须让对应 `lib/*.jar` 进入 classpath，否则 `git4idea.*` 类不可见。若用户禁用 Git 插件，本插件不会被加载（依赖不满足），不会报错——符合预期。

## 5. 风险清单

| ID | 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|---|
| R1 | 非模态提交流程下，`beforeCheckin` 中弹模态框出现焦点/线程异常（社区有 `Thread context was already set` 报告） | 中 | 高 | **POC 第一项验证**；降级方案：改为 `Notification` + `CANCEL`，或引入 Kotlin `CommitCheck` |
| R2 | 用户禁用插件即可绕过，被误当作安全管控 | 高 | 中 | 产品定位写入需求文档；同时配置服务端保护分支 |
| R3 | 多仓库项目（multi-root）分支不一致 | 中 | 中 | 按仓库分别判定，任一不合规即阻断，并列出全部违规仓库 |
| R4 | merge 判定漏判：`--amend` 合并提交、squash merge、rebase 后提交 | 中 | 中 | 规则边界写入文档；v1.1 增加"提交父节点数 > 1"二次校验 |
| R5 | 平台 API 演进（`CommitCheck` 取代 `beforeCheckin`） | 低 | 中 | 拦截逻辑收敛在 1 个类；预留替换路径 |
| R6 | 编译目标与 IDE 运行 JDK 不匹配（class 69 vs 61/65） | 低 | 高 | 固定用 2026.2 SDK + `--release 25`；CI 跑 Plugin Verifier |
| R7 | 内部分发与签名 | 低 | 低 | 内网 Marketplace / 离线 zip；离线包需签名时用 `marketplace-zip-signer` CLI |
| R8 | 提交面板混入非 Git 仓库文件（SVN 混合项目） | 低 | 低 | `getRepositoryForRoot` 返回 null 时跳过，不误伤 |
| R9 | Maven 无官方支持，构建链需自建，`runIde`/`verifyPlugin` 需手工替代 | 高 | 中 | 已在 §4.2.1 明确边界；构建脚本按开发文档 §8 一次搭好，后续零维护 |
